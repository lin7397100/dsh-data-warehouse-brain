# sg-ontology-modeling · 生产域本体建模

## 定位

把 DB2 仓库的物理结构翻译成**机器可读的业务语义**，为语义解析、DSL 编译、根因下钻提供底座。

## 建模数据来源

| 来源 | 内容 | 路径变量 |
|---|---|---|
| ① ODS 层表结构 | 55 个源系统表的实体与属性 | `$DB2_ASSETS_HOME/DDL` |
| ② GZPROD 存储过程 | 55 个生产过程的业务计算逻辑 | `$DB2_ASSETS_HOME/PROD` |

## 解析模式（四选一，按过程复杂度）

| 模式 | 适用 | 产出要素 |
|---|---|---|
| **A 直查式** | 单表直出指标 | 源表 / 过滤条件 / 聚合方式 |
| **B 单链 CTE** | 单一 CTE 链（T1→T2→…） | 每步业务含义 / 字段派生 |
| **C 多链合并** | 多 CTE 链 UNION / JOIN | 链间关系 / 合并口径 |
| **D 跨过程依赖** | 过程调用过程 | 调用顺序 / 中间表落点 |

## 工作流（五步）

### Step 1 · 实体提取（ODS 层）

扫描 `SMBB_M_O_XXX` 表结构，提取实体与属性：

| 实体 | 典型属性 |
|---|---|
| 高炉 | 炉座号、铁次、风量、风温、焦比、煤比、利用系数 |
| 轧机产线 | 轧制计划号、生产时间、出入标志、钢种标志 |
| 转炉 | 炉座号、炉次、装入量、吹炼时间、终点温度 |
| 班组 | 班组组别、班次、作业时间 |
| 钢种 | 钢种代码、钢种标志、规格 |
| 能源介质 | 介质代码、消耗量、单价 |

输出：`{entity, source_table, attributes[], keys[]}`

### Step 2 · 过程解析（GZPROD 55 个）

逐个过程提取：

1. **数据流向**：输入 ODS/DWD 表 → 输出 DWD/DWS 表
2. **CTE 计算链业务含义**：例（圆棒 P/Y 日作业率）
   `T1(计划×钢种关联) → T2(时间窗过滤) → T3(班次起始) → T4(班次截止) → T5(前置时间) → 作业率计算 → 指标写入`
3. **DECODE 业务映射**：炉座代码、班组组别、产线代码 → 业务含义
4. **指标聚合口径**：SUM/COUNT/AVG 的分组维度与时间粒度

### Step 3 · 四元组构建

```json
{"entities": ["轧机产线", "轧制计划", "钢种", "班组"],
 "relations": ["轧机产线-执行-轧制计划", "轧制计划-关联-钢种", "班组-操作-轧机产线"],
 "processes": [{"name": "P_DWS_FACT_ZZGZ_ZG01", "chain": ["T1", "T2", "T3", "T4", "T5"],
                "logic": "五步计算日作业率 → 指标写入"}],
 "metrics": [{"zb_code": "2000514", "zb_name": "质量_圆棒当日合格量", "owner_entity": "轧机产线"}]}
```

### Step 4 · 本体血缘生成

`KPI → 语义定义 → DWS 表 → 存储过程 → ODS 源表`，双向可查（KPI 下钻 / ODS 上卷）。

### Step 5 · 交叉验证与版本化

- 与元数据专家的物理血缘比对，不一致必须查明
- 本体文件按业务域拆分落盘（`$ONTOLOGY_HOME/本体图谱-{域}.json` + `.md`）
- 版本号递进，变更影响的高频 KPI 清单同步给语义专家

## 建模范围优先级

1. 轧钢 ZG01 → 2. 炼铁 LT01 → 3. 炼钢 LG01 → 4. 原料 YL01 → 5. 采购管制 CGGZ_0001
（覆盖约 80% 高频 KPI）

## 输出规范

- 实体清单 + 关系 + 计算过程 + 指标映射（JSON + Markdown 双格式）
- 每个高频 KPI 的本体血缘链
- 解析报告：数据流向 / CTE 业务含义 / DECODE 映射 / 聚合口径 / 不确定项（`待确认`）

## 注意事项

1. **纯解析工作流，不调用 MCP** —— 只读 DDL 与过程源文件，不查业务数据。
2. **禁止臆造业务含义**：不确定的映射标注 `待确认`，不编造。
3. 路径走环境变量 `$DB2_ASSETS_HOME` / `$ONTOLOGY_HOME`，禁止硬编码绝对路径。
4. 与元数据专家物理血缘冲突时，以 DB2 实数据核验结果为准。
