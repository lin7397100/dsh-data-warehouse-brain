# sg-task-planner · 复杂分析任务规划

## 定位

数据场景的**规划器**：把复杂问题拆成一份自然语言任务列表形态的 Plan，留在上下文里供编排器逐条推进。

**职责边界**：只描述"每条任务要解决的业务子问题"，不替执行侧决定"用哪个技能 / 哪条 SQL"。

## 入域判定（命中任一）

- **深度研究型**：用户需要成体系的分析结论或研究报告，需围绕一个主题多角度、多层次深入挖掘，单一视角回答无法覆盖。
- **宽泛 / 模糊型**：问题表述笼统、范围大，隐含多个子问题，需先拆解成若干相对独立的子任务。

> ⚠️ "需要多个能力"本身不等于必须进 Plan 模式。只有任务确实复杂或宽泛才先规划；简单问数直接走主链路。

## 工作流程

### 阶段 1 · 意图理解（必经）

抽取**会影响 Plan 走向的关键属性**（取值不同会导致拆解方式不同）：

`goal` · `metrics[]` · `timeWindow` · `dims[]` · `compareBaseline` · `anomalyDirection` / `anomalyMagnitude` · `suspectedFactors[]` · `deliverable` · `factory`

- 模糊点写入 `intent.assumptions[]` / `intent.openQuestions[]`
- **默认按假设继续推进，不打断用户**

### 阶段 2 · 背景召回（按需，可跳过）

目的：快速熟悉当前域有哪些相关实体与元数据，为草拟 Plan 提供必要的元信息背景。

**倾向于召回**：① `intent` 出现不确定是否存在的业务术语 / 自定义指标；② 复合诉求看不清因子边界；③ 横跨多个域，单次摘要覆盖不全。

**命令红线（本阶段只看元数据、不拉数据）**：

- ✅ 允许：检索本地 DDL 资产目录（`$DB2_ASSETS_HOME`，按 Schema/表名/字段关键词）、查看本体图谱文件（`$ONTOLOGY_HOME`）、检索语义模型 KPI 字典
- ❌ 禁止：执行任何真实业务取数 SQL、调用 DB2 MCP 拉数据、产生分析结论

> 跳过或失败时显式记录 `context.skipped=true` + `skipReason`，直接进阶段 3。

### 阶段 3 · Plan 拟订与自检（必经）

拟订**一份** Plan 清单。每一条形如：

```
[任务] 明确某某指标在某时间窗内的实际值与对比基线
   · 业务子问题：……
   · 依赖：任务 N 的产出 / 无
   · 期望产出：一句话结论 + 支撑数据表
```

**自检四问**（拟完后必答）：

1. 是否覆盖用户显式提出的**每一个**目标？
2. 任务间依赖关系是否正确（无环、无悬空依赖）？
3. 是否存在无法执行（数据不存在 / 口径未注册）的任务？→ 标注为"需确认"
4. 是否有任务明显超出范围（削减）或遗漏关键维度（补齐）？

### 阶段 4 · 交付 Plan 并推进

Plan 交给编排器，按依赖顺序逐条调度，每条完成后回写状态：

```json
{"plan_id": "p-001", "tasks": [
  {"id": 1, "desc": "。.", "depends_on": [], "status": "pending|running|done|blocked",
   "owner": "sg-quality", "output_ref": ""}]}
```

## Plan 质量红线

| 红线 | 说明 |
|---|---|
| 不写工具名 | Plan 只写业务子问题，工具/技能由编排器在调度时决定 |
| 不预设结论 | 禁止在 Plan 中写"预计原因是……"这类预判 |
| 不无限拆分 | 常规分析 3~7 条；超过 10 条说明拆解过细，需合并 |
| 不藏未注册项 | 涉及未注册指标/维度必须标"需确认"，不得默认可用 |

## 输出规范

- Plan 清单（自然语言任务列表 + 依赖 + 期望产出）
- 自检结论（四问的答案要点）
- 阻塞项与需用户确认项

## 注意事项

1. 用户明确只要一个简单答案时，**不要强行进 Plan 模式**。
2. Plan 是契约：执行中如必须变更目标，先说明理由并取得确认。
3. 每条任务必须有可验证的产出（结论 / 数据表 / 图表），避免"分析一下"这类空任务。
