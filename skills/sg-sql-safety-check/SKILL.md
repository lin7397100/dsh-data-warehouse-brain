# sg-sql-safety-check · SQL 安全审查（四层护栏）

## 定位

所有要落到 DB2 上执行的 SQL 的**必经闸门**。

## 四层护栏

### ① 语法级（直接拦截）

| 拦截对象 | 关键词 |
|---|---|
| 数据删除 | `DELETE` |
| 表结构变更 | `DROP` `TRUNCATE` `ALTER` |
| 权限变更 | `GRANT` `REVOKE` |
| 数据写入 | `INSERT` `UPDATE` `MERGE` |
| 存储过程执行 | `CALL`（需审批） |

> 命中即拦截，**不进入下一层**。

> **语句级判别（2026-11-05 治理侧修订，撤回早前把 REPLACE 塞入裸词黑名单的提法）**：
> `REPLACE` **不列入裸词黑名单** —— DB2 的 `REPLACE(...)` 是合法标量函数，裸词拦截会误杀
> 只读查询。仅当语句形态为 `REPLACE INTO` 时按写操作拦截；`ADMIN_CMD` 等可执行过程调用
> 同样按语句级拦截，不按裸词匹配。

> **P0 高危专项（核心配置表 DDL）**：`T_ADS_DIM_GZ01`（指标配置表）等核心配置 / ADS / DWS 表的
> `DROP` / `TRUNCATE` / `ALTER` / `DELETE` / 删表 / 重建 / 清表，**无论以何种自然语言表述（"删掉重建""清空配置表"等）一律硬拒**，
> 不进入审批层、不提供改写建议，直接返回拒绝并提示走变更流程。

### ② 资源级

| 项 | 限制 |
|---|---|
| 超时 | ≤ 30 分钟 |
| 返回行数 | ≤ 1 亿行（超过需聚合或分批） |
| 分区条件 | 大表**必须**带 `YMD` 或分区键条件 |
| 分页 | 明细查询必须带 `FETCH FIRST n ROWS ONLY` |

超限 → 拦截 + 给改写建议（加分区条件 / 加聚合 / 缩时间窗）。

### ③ 权限级

- 只读服务账号执行，禁止使用具有写权限的连接
- 禁止跨授权 Schema 访问（成本域 `CB00` 需单独授权）
- 敏感表访问需白名单校验

### ④ 审批级

任何写操作（含配置写入、过程部署）**必须人工确认**：

```
⚠️ 检测到写操作
  操作类型：INSERT
  目标表：SMBB_M_A_GZ01.T_ADS_DIM_GZ01（指标配置）
  影响范围：新增 1 条指标配置
  执行前需用户明确确认（回复"确认执行"后继续）
```

### ⑤ 设计态资产变更（口径 / 计算逻辑）

指标口径、计算逻辑、配置表内容属于**设计态资产**，不归问答会话管辖：

| 变更类型 | 识别特征 | 处置 |
|---|---|---|
| 成本口径变更 | "改 / 修改 / 调整 / 变更 … 计算口径 / 计算 / 口径"，"重算口径""换口径" | **拒绝自动执行** + 触发卡点 + 双人复核（协同 `sg-cost-ops`） |
| 指标口径漂移 | "用 X 口径重算 / 换口径" | 显式确认后方可，且须标注口径来源 |

> 任何"改一下铁水成本的计算口径""调整某指标计算逻辑"类请求，**禁止直接执行**，必须回到变更流程（建任务 → 双人复核 → 版本化）。

### ⑥ 问数通道轻量护栏（白名单模板 · 10ms 静态校验）

> **场景**：Q1/Q2 类问数（见 team-lead SOP Q1-Q5）。该类占问数流量 70%+，不应派 `sg-governance` 全护栏（L2-L4 逐条审查）。

**白名单模板（本地正则 + 行数守恒断言，≤10ms 通过即放行，不派 sg-governance）**：

| 校验项 | 规则 |
|---|---|
| 动词 | 仅 `SELECT`（禁 `INSERT`/`UPDATE`/`DELETE`/`MERGE`/`DROP`/`ALTER`/`TRUNCATE`/`CALL`/`GRANT`/`REVOKE`） |
| 时间窗 | 必须带 `YMD` 或分区键条件（禁全表扫描） |
| Schema | 单 schema（禁止跨授权域；成本域 `CB00` 仍需单独授权） |
| 分页 | 明细查询必须带 `FETCH FIRST n ROWS ONLY` |
| 模板 | 命中 `REGEXP_LIKE` 静态白名单：`SELECT … FROM <单schema表> WHERE YMD… [AND …] [FETCH FIRST …]` |

**⑥ 与 ① 的一致性**：本行动词清单与 ① 完全相同，`REPLACE` 只拦 `REPLACE INTO` 语句形态，
不拦 `REPLACE()` 函数；其余写关键字按词边界匹配（`sg_db2_gateway.py` / `sgdw_sql_exec.py` 同口径）。

**逃逸条件（非模板 → 升级全护栏 L2-L4）**：命中写操作 / 跨 schema / 无时间窗 / 动态 SQL（`EXECUTE IMMEDIATE` / `PREPARE..FROM`）/ 核心配置表 DDL → 一律回到 ①~④ 四层全护栏，必要时人工确认。

> **原则**：本分支是"问数通道"的加速，**不改 L3/L4 全档**。④ 审批级、③ 敏感表、P0 高危专项（如 `T_ADS_DIM_GZ01` 等核心配置表 DDL）在任何分支均硬拒，不可绕过。

## 工作流

### Step 1 · 逐层检查

按 ①→②→③→④ 顺序，任一层拦截即输出结论、停止后续检查。

### Step 2 · 判定敏感级别

涉及表的数据分级（L1~L4），成本明细类为 L4 需脱敏/限权。

### Step 3 · 输出结论

| 结论 | 内容 |
|---|---|
| 通过 | 可直接执行（附 SQL 与预计扫描量） |
| 拦截 | 层级 + 原因 + **具体改写建议** |
| 需审批 | 写操作说明 + 影响范围 + 等待人工确认 |

### Step 4 · 审计落盘

`{时间, 主体(用户/专家), 对象(SQL 摘要), 操作类型, 访问范围, 审查结果}`

## 输出规范

```json
{"verdict": "pass|blocked|need_approval",
 "layer": "① 语法级|② 资源级|③ 权限级|④ 审批级",
 "reason": "…", "suggestion": "…",
 "sensitive_level": "L4", "masking_required": true,
 "audit_id": "AUD-20260901-001"}
```

## 注意事项

1. **只读账号是铁律**，任何写操作一律拦截并提示人工确认，不绕过。
2. **不得"先执行后补审"**。
3. 拦截时给可执行的改写建议，不只说"不行"。
4. 审查规则变更需版本化并记录，防误放行。
