# sg-sql-optimizer · SQL 优化与规范审查

## 定位

慢查询的**诊断与处方**：不只给结论，给可执行的改写方案与预期收益。

## 优化清单（DB2 方言）

### 1. 分区条件（最高优先级）

| 问题 | 处方 |
|---|---|
| 大表无分区条件 | 强制注入 `YMD` / 分区键 |
| 分区键上套函数 | 改为范围条件（`YMD BETWEEN`） |
| 分区键隐式转换 | 字符与数值/日期对齐 |

### 2. 索引与 JOIN

- JOIN 字段类型一致（避免隐式转换导致索引失效）
- JOIN 顺序：小表驱动大表（DB2 优化器通常自动处理，但复杂场景需提示）
- 复合索引字段顺序与查询条件对齐

### 3. 聚合与去重

| 问题 | 处方 |
|---|---|
| `DISTINCT` 滥用掩盖重复 | 先查重复根因（JOIN 放大），再去重 |
| 大结果集 `ORDER BY` | 加 `FETCH FIRST` 或先聚合再排序 |
| 子查询重复计算 | 提为 CTE 复用 |

### 4. UNION

- 无去重需求时用 `UNION ALL`（省去排序去重开销）
- `OR` 条件改写为 `UNION ALL`（常能启用索引）

### 5. 隐式类型转换

字符日期与 DATE 比较、数值与字符比较 → 显式转换到字段侧或常量侧一致。

### 6. 统计信息

大表批量加载后提示 `RUNSTATS`，保证优化器拿到最新统计。

### 7. 返回量控制

- 禁 `SELECT *`
- 明细查询默认 `FETCH FIRST n ROWS ONLY`
- 报表类用聚合代替明细传输

## 工作流（四步）

### Step 1 · 收集信息

SQL 文本 + 表结构（分区键/索引）+ 数据量 + 执行频率 + 当前耗时。

### Step 2 · 问题定位

按上述七项逐条检查，输出问题清单（按影响排序）。

### Step 3 · 改写方案

每条问题给：原写法 → 改法 → 原因 → **预期收益**（定性：高/中/低，避免虚假精确）。

### Step 4 · 验证建议

- 用 `EXPLAIN` 对比改写前后（只读，不执行写操作）
- 抽样小时间窗试跑对比耗时
- 无法验证时明确说明"建议项未实测"

## 输出规范

```
【问题 1】大表无分区条件（影响：高）
  原：SELECT … FROM T_DWS_FACT_XXX WHERE ZB_NAME=?
  改：SELECT … FROM T_DWS_FACT_XXX WHERE ZB_NAME=? AND YMD BETWEEN '20260801' AND '20260831'
  因：分区裁剪，扫描量从全表降至单月
  预期收益：高｜验证：EXPLAIN 对比 + 单月试跑
```

## 规范审查附加项

| 项 | 要求 |
|---|---|
| 只读性 | 无写操作（写操作需审批） |
| 字段显式 | 禁 `SELECT *` |
| 分母保护 | 除法 `NULLIF` |
| 分页 | `FETCH FIRST n ROWS ONLY` |
| 注释 | 复杂 CTE 带业务注释 |

## 注意事项

1. **不臆造执行计划数据** —— 未实测的收益标注"预估"，不给虚假精确数字。
2. 优化不得改变语义：改写后结果必须与原 SQL 一致（除明确说明的近似优化）。
3. 涉及索引创建/统计信息更新属写操作，需治理专家审批 + 人工确认。
