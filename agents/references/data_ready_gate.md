# 数据就绪门禁与质量异常判定矩阵

> 作用：在根因分析与质量异常诊断**开始之前**，先回答一个前置问题——**"这到底是业务真异常，还是数据没就绪？"**
> 定位：`disciplines.md §11` 的前置判断层；`sg-quality` 与 `sg-root-cause-fullchain` 的必查项
> 铁律级：与 §10/§11/§12 同级；跳过本门禁直接下"业务异常"结论 → 结论作废

---

## 一、为什么需要这道门禁

数仓里的"异常"至少有两类，处理方式完全相反：

| 类型 | 表现 | 正确处理 | 错误处理 |
|---|---|---|---|
| **业务真异常** | 数据完整、时序正常，值确实偏离 | 进入归因分析（§12） | — |
| **数据未就绪** | 值缺失/为 0/只到一半 | 定位断在哪个环节（抽数？过程？落表？） | 误判为"停产/设备故障"，对外发错结论 |

**典型事故形态**：批处理 05:48 才落表，而查询在 05:30 执行 → 查到的是昨天数据或空值 → 被解释成"产量骤降"。
另一形态：同一账期过程跑了 3 次，前 2 次因 ODS 未到齐而空跑成功，第 3 次才写入真值 → 若只看第 1 次执行记录，会误判"加工失败"。

## 二、三层门禁（顺序不可颠倒）

### G1 · 批处理是否成功

```sql
-- CREATER 过程同 schema 下的作业日志
SELECT START_TIMESTAMP, LAST_TIMESTAMP, ELAPSED, IS_SUCCESSFUL,
       PARAM_INFO, ERROR_DESC
FROM <CREATER_SCHEMA>.T_PUB_JOB_LOGS
WHERE P_DATE = '<账期>'
ORDER BY START_TIMESTAMP DESC;
```

判读要点：

| 现象 | 含义 |
|---|---|
| `IS_SUCCESSFUL='Y'` 且仅 1 条 | 正常单次执行 |
| 同一 `P_DATE` 多条记录 | **重试**：需看最后一条是否 `Y`；前几条可能是空跑 |
| 末条 `IS_SUCCESSFUL='N'` | 加工失败 → 查 `ERROR_DESC`，此时**禁止**做业务归因 |
| `ELAPSED` 显著高于历史均值 | 数据量异常或锁等待 → 影响落表时间 |
| `PARAM_INFO` 为空或与账期不符 | 参数未传对，实际未加工该账期 |

### G2 · 抽数是否完整

```sql
-- ETL 抽数日志（作业号从权威台账 schema_region_mapping.json 取）
SELECT * FROM SMBB_M_A_CS01.V_PUB_JOB_LOGS_LD_1D_X
WHERE DES_OBJECT_NAME = '<ODS表名>'
  AND P_DATE = '<账期>';

-- ODS 入仓时间覆盖范围
SELECT MIN(REC_CREATE_TIME) AS FIRST_IN, MAX(REC_CREATE_TIME) AS LAST_IN, COUNT(*) AS ROWS_CNT
FROM <ODS_SCHEMA>.<ODS表>
WHERE <日期列> = '<账期>';
```

判读要点：

| 现象 | 含义 |
|---|---|
| `LAST_IN` 晚于预期（如次日凌晨才到） | 抽数延迟 → 下游全链顺延 |
| 记录数明显低于邻日（如仅 1/4） | **半批次**：源系统只推了部分数据 |
| `DU_TIME` 为空且业务表应有 | 上游未更新 → 数据为旧值 |
| 作业号与 schema 不匹配 | 查错了作业（schemA→LD_COM 映射必须查台账） |

### G3 · 落表时序是否早于查询时刻

```sql
-- DWS 层
SELECT MIN(LOAD_TIME) AS T1, MAX(LOAD_TIME) AS T2, COUNT(*) AS CNT
FROM <DWS表> WHERE <日期列> = '<账期>';

-- ADS 层
SELECT MIN(CREATE_TIME) AS T1, MAX(CREATE_TIME) AS T2, COUNT(*) AS CNT
FROM <ADS表> WHERE <日期列> = '<账期>';
```

判读要点：

- `LOAD_TIME` / `CREATE_TIME` **晚于**查询执行时刻 → 当时查的是旧数据或空值 → **未就绪**，不是业务异常
- 同一账期出现**多段**时间戳（如 05:48 与 09:12 两批）→ 存在补数或重跑，需取最后一批
- 各基地落表时间不同 → 跨基地对比时可能"一边有数一边没数"，属时序问题而非业务差异

## 三、质量异常 → 埋点判定矩阵

按现象直接查对应层，**不要从头六步走一遍**。

| 现象 | 第一嫌疑层 | 关键查证 | 可能的结论 |
|---|---|---|---|
| 值为空 / NULL | G3 落表 | 该账期是否有落表记录 | 未就绪 / 该维度本无数据 |
| 值为 0 且邻日非 0 | G1 + G3 | 作业是否成功、落表时间是否正常 | 真 0（真停产）/ 半批次 / 空跑覆盖 |
| 只有部分基地有数 | G2 抽数 | 各基地 ODS `REC_CREATE_TIME` | 单基地抽数延迟 |
| 记录数只有邻日 1/N | G2 抽数 | `COUNT(*)` 对比邻日 | 半批次（源系统分批推送） |
| 数值量级突变（10 倍/0.1 倍） | G2 + G3 | 单位换算、是否取到汇总口径、是否补数重算 | 口径错 / 重跑覆盖 / 单位问题 |
| 同一天出现两个不同值 | G1 重试 | 同 `P_DATE` 多次执行的时间戳 | 重跑覆盖，取最后一次 |
| 数据"延迟一天" | G2 | `LAST_IN` 与调度周期 | 抽数延迟（T+1 未完成） |
| 加工耗时异常拉长 | G1 | `ELAPSED` 与历史均值 | 数据量激增 / 锁等待 / 资源争用 |

## 四、六类结论口径（必须四选一，禁止含糊）

| 结论 | 判据 | 后续动作 |
|---|---|---|
| **真 0 / 真异常** | 三层门禁全部通过，数据完整且时序正常 | 进入 §12 归因分解 |
| **未就绪** | 落表时间晚于查询时刻，或该账期无落表 | 说明"数据尚未就绪，预计 X 时可查"，不调用业务归因 |
| **半批次** | ODS 记录数显著低于邻日 | 定位源系统推送批次，标注数据完整度 |
| **重跑覆盖** | 同账期多次执行/多段落表时间 | 以最后一次为准，说明覆盖关系 |
| **补数缺失** | 有调度计划但该账期无执行记录 | 提数据修复任务，不解释业务 |
| **口径错** | 三层均正常，但与其他口径不一致 | 转口径核验（`caliber_check.md`） |

## 五、与全链路追溯（§11）的关系

```
查询结果异常
   ↓
【本门禁 G1→G2→G3】← 先判"是否数据问题"，成本最低（3 条 SQL）
   ├─ 数据问题 → 定位到具体环节，输出结论 + 修复任务，结束
   └─ 数据没问题 → 进入 §11 六步全链路追溯 → 再进 §12 归因分解
```

**顺序铁律**：门禁在三层埋点之上，**便宜的先查**。§11 的完整六步（含过程源码解析）成本高，应在门禁排除了数据问题后再走。

## 六、禁止事项（违反即结论作废）

| # | 禁止 | 原因 |
|---|---|---|
| 1 | 只看结果表就判"产量下降/停产" | 未排除未就绪 |
| 2 | 用"应该是没数据"解释 0 值 | 必须给出 G1/G2/G3 中哪一环的实证 |
| 3 | 同账期多次执行时只取第一条日志 | 可能是空跑，真值在最后一次 |
| 4 | 跨基地对比时不看各基地落表时间 | 一方未就绪会造成"差异"假象 |
| 5 | 门禁未通过就进入归因分解 | 归因结论建立在错误数据上，全部作废 |
| 6 | 只查 ETL 日志不看过程日志（或反之） | 两层分属抽数与加工，缺一无法定位 |

---

## 七、最小执行清单（根因/质量异常必做）

```
□ G1 查 T_PUB_JOB_LOGS：当日作业是否成功、是否重试、耗时是否异常
□ G2 查 V_PUB_JOB_LOGS_LD_1D_X + ODS REC_CREATE_TIME：抽数是否完整、是否延迟
□ G3 查 LOAD_TIME / CREATE_TIME：落表是否早于查询时刻、是否有多批
□ 四选一给结论：真异常 / 未就绪 / 半批次 / 重跑覆盖
□ 未就绪与半批次必须写明"预计可查时间"或"缺失范围"
□ 只有判定为"真异常"才可进入 §12 归因
```
