### 10. 根因分析数据纪律（2026-10-15 用户铁律 · 最高优先级 · 不可降级）

本专家团进行任何数据异常根因分析时，**必须且只能**遵循以下纪律。违反任一条的根因结论一律作废，退回重做。

**10.1 禁用模糊措辞**
禁止使用以下字眼：`可能`、`大概`、`疑似`、`估计`、`推测`、`或许`、`应该`、`大约`。数据结论只有对与错，没有中间地带。

**10.2 精准定位规范**
每条结论必须指明：
- **具体表名**（完整 `SCHEMA.TABLE` 格式）
- **具体字段名**
- **时间区间**（精确到日，如 `20261014`，必要时精确到 `YYYYMMDDHHMMSS`）
- **对比基准**（哪个值是参考标准、为什么它是标准）

**10.3 差异量化规范**
必须用数值表达差异：`实际值 = X` vs `预期值 = Y`，偏差 = `|X-Y|`，偏差率 = `|X-Y|/Y × 100%`。不可仅用"偏高""偏低""异常"等定性描述。

**10.4 证据链追溯规范**
每一条结论必须附可追溯证据：
- 数据来源（SQL 查询语句或存储过程名）
- 查询结果（实际返回的行/值）
- 交叉验证（至少两个独立来源对拍，如 DWS vs ODS 直算）

**10.5 输出结构强制格式**

```
【异常现象】
  - 指标名称（ZB_CODE/ITEM_NAME）
  - 异常值 vs 基准值（量化差异）
  - 发现时间

【精准定位】
  - 表：SCHEMA.TABLE
  - 字段：COLUMN_NAME
  - 时间：YYYY-MM-DD ~ YYYY-MM-DD
  - 范围限定：WHERE 条件

【差异量化】
  - 实际值：X（来源：TABLE.COLUMN，SQL 语句）
  - 预期值：Y（来源：TABLE.COLUMN，SQL 语句）
  - 偏差：|X-Y| = Z
  - 偏差率：Z/Y × 100% = W%

【根因证据链】
  - 证据1：ODS 层直算结果（SQL + 返回值）
  - 证据2：DWS/DWD 层中间结果（SQL + 返回值）
  - 证据3（如有）：过程 SQL 片段定位（表名 + 行号 + 关键 WHERE/JOIN 条件）
  - 裁定：明确指出哪一步、哪个条件导致偏差，偏差是否可接受
```

**10.6 不确定时不编造**
如果当前证据不足以给出确定性结论，只能输出以下三种状态之一：

- `[已证实]` — 证据链完整且经 DB2 实数据核验，**confidence 无上限**（可达 1.0）
- `[证据不足]` — 已有部分证据但不足以定论，明确指出缺哪些证据，需要查阅哪些表/过程，**confidence ≤ 0.60**（禁止配 ≥0.6，必须转 L2 跨专家会诊）
- `[无法查证]` — 现有条件下不可获取证据，如实说明原因并给出解锁路径，**confidence ≤ 0.40**（禁止作确定值交付）

**证据分级→置信度上限绑定（2026-11-05 P1-9 新增）**：
| 证据状态 | 置信度上限 | 处置要求 |
|---|---|---|
| 三源（ODS+CDM+ADS）全链路实数据核验通过 | **≤ 1.0**（无上限） | 正常交付 |
| 双源核验通过（缺一层） | **≤ 0.80** | 标注缺失层 + 降级说明 |
| 单源核验（仅 ADS 直查） | **≤ 0.65** | 标注「仅单源，无交叉验证」 |
| 证据链不完整 / 仅部分溯源 | **≤ 0.60** | 强制转 L2 跨专家会诊 |
| 不可查证 | **≤ 0.40** | 禁止当确定值交付 |
- `[已证实]` — 证据链完整，结论确定
- `[证据不足]` — 列出已有证据 + 明确指出缺哪些证据 + 需要查阅哪些表/过程
- `[无法查证]` — 说明技术限制（如过程体过大无法完整读取）+ 给出替代验证路径

禁止在证据不足时给出看似完整的结论。禁止用业务经验替代数据查证。

> 本条款优先级高于所有其他工作流规则。根因分析走 Workflow B 时，`sg-quality`（砺真）负责按本条款逐条核查；编排器汇总阶段未通过核查的根因结论禁止交付。

### 11. 数据埋点全链路追溯纪律（2026-10-16 用户铁律 · 与第10条同级 · 不可降级 · 2026-11-02 升级为「数据全链路生命周期强制」）

**查数据不是随便查**——必须有明确依据，从最初的数据源开始，一步一步到数据展示，**链路不能断、要连续**。任何指标的数据追溯必须走以下六步标准路径，跳步或断链的结论一律作废。

**11.-1 数据全链路生命周期强制（2026-11-02 用户铁律 · 五项硬约束）**

> 用户定律：**血缘不足、链路没连续贯通，数据就会存疑。数据全链路生命周期的完整与准确，是数仓智脑专家团中最主要的事。**
> 本项**优先于**任何快线降级、SLA 压缩与编排器便利化判断。

| # | 硬约束 | 违反后果 |
|---|---|---|
| **C1** | **三层必须齐全或合法降级**：`T_ODS` → `T_DWD/T_DWS` → `T_ADS`；缺层须显式标注。**无 T_ADS、直接用 CDM(DWD/DWS) 展示是合法终点**，只要 ODS→CDM 连续，不得判为断链 | 标 `[结构缺失]`，结论存疑 |
| **C2** | **tmp 临时表必须解析纳入**：过程内 `tmp*`/GTT 是链路合法一环，承载中间计算，**不得跳过、不得当噪声**。`SYSCAT.ROUTINEDEP` 静态依赖残缺须如实标注，**不得补造** | 标 `[tmp未解析]`，加工链路不完整 |
| **C3** | **链路必须连续可核验**：每层上下游须有实据（SQL1 / CREATER / ROUTINEDEP / 实查对账），**禁止臆断映射** | 标 `[链路断裂@<层>]` → 转断链兜底 |
| **C4** | **血缘三闸门必过**：①结构完整 ②链路连续 ③设计态-数据态一致（对照 K7 5S 规范）。任一不过 → 存疑，不得作确定值交付 | 不得交付确定结论 |
| **C5** | **断链必兜底**：反向追溯断链 → 走 `agents/references/lineage_fallback.md` 正向建模，**禁止手搓/静默出数**，产物标 `[正向建模·待实据核验]` | 结论作废 + 记违规 |

**血缘三闸门（交付前必过）**：

```
闸门① 结构完整     → T_ODS / T_DWD·T_DWS(+tmp) / T_ADS 三层齐全 或 合法降终点到 CDM
闸门② 链路连续     → 无断点、无臆断映射（每层有实据）
闸门③ 设计态≡数据态 → 指标卡/本体 与 DB2 实数据对照 K7 5S 规范核验
任一不过 → 标存疑 + 说明缺哪一环；断链另转 lineage_fallback
```

**消费纪律**：下钻 / 趋势 / 报表 / 根因**一律消费标准血缘 JSON**（schema 见 team-lead.md 第零铁律），**禁止任何消费层（含编排器）手搓近似血缘**。T2a 快线同样适用：趋势可快，**点开任意数据点必须走完整血缘引擎**。

**⚠ WeKnora 大流量纪律**：检索 5S 规范用 K7（`d12f3c32-bf50-41cc-8be8-77af4c45bb35`）；`match_count` 建议 ≤3（返回值可达 97–186KB，防 11115 溢出）；不可用则降级本地 `knowledge/5s/`，记 `weknora_status=down` 并披露。

**11.0 前置门禁（2026-10-30 增补 · 先于六步执行）**

在下钻六步之前，先用 3 条 SQL 排除"数据未就绪"：G1 批处理是否成功（`T_PUB_JOB_LOGS`）→ G2 抽数是否完整（`V_PUB_JOB_LOGS_LD_1D_X` + ODS `REC_CREATE_TIME`）→ G3 落表是否早于查询时刻（`LOAD_TIME` / `CREATE_TIME`）。
详见 `agents/references/data_ready_gate.md`。**顺序原则：便宜的先查** —— 门禁 3 条 SQL 即可排除大半"假异常"，避免动辄解析过程源码。

**11.1 六步标准路径（顺序不可颠倒、不可跳步）**

```
Step 1 定指标 → Step 2 验血缘 → Step 3 解过程
                                    ↓
Step 6 查落表 ← Step 5 查过程日志 ← Step 4 查抽数
       ↓
  产出 HTML 时间线报告（三层埋点齐全）
```

**Step 1 · 定指标（多源定位，禁止单源锁死）**

指标定位必须按以下**三级降级顺序**尝试，禁止只查一个来源就下结论：

**① 优先查「三钢指标注册表」**（本地 `artifacts/registry_site/indicator_api.json`，3775 KPI / 161 数据集 / 959 公式 / 9 语义别名）：
- `aliases[]`：用户口语 → 标准名 → 公式 → base_kpis[]（如"入炉铁温"→折算铁温→6个base_kpis）
- `lookup`：按 Sheet!Cell 查公式
- `kpi`：按 KPI 编码查数据集绑定
- 命中复合指标（base_kpis 非空）→ 拆解出全部基础 KPI，逐个走后续步骤

**② 未命中 → 查 `SMBB_M_A_GZ01.T_ADS_DIM_GZ01`**（ZB_CODE/ZB_NAME/FACTORY_DIV/FACTORY_FLAG/SQL1/SQL2/CREATER，IS_VALID='3'）：
- **禁止模糊匹配后直接取第一条结果**——同名/近名指标可能跨域（实例：石灰石日消耗量 6063300 在原料域 YL01 ≠ 石灰耗 6013001 在炼钢域 LG01）
- 记录 FACTORY_FLAG（QZ=泉州/空=本部），它决定 T_PM_KPI 写入的时间门控

**③ 仍未命中 → 查三份指标血缘文档**（很多指标没有 ZB_CODE，只存在于 cpt 报表内嵌数据集中）：
- Grep `ZZGZ_指标血缘.md` / `ZZGZ_JD02_指标血缘.md` / `GZJD02LDY_指标血缘.md`
- 从数据集 SQL 中提取 KPI_ID 段与源表（如 QZ_SCRB 数据集限 6009800-6014000）
- 此类指标无 T_ADS_DIM_GZ01 注册，CREATER 需从血缘文档中取

**④ 全部未命中 → 触发断链兜底，不得输出 `[证据不足]` 了事**（2026-11-02 依第零铁律推论5 修正）

```
三源均未命中 → 自动升 lineage_fallback（详见 agents/references/lineage_fallback.md）：
  S1 用户业务规则（会话内自然语言 / 上传文档，须含指标码+口径+生效期）
  S2 weknora K4 业务规则库 6838e00b-fb8e-4de3-9f08-425af71dbdbd（hybrid_search RULE-*）
  S3 weknora K7 大数据5S平台知识库 d12f3c32-bf50-41cc-8be8-77af4c45bb35（★必查，建模方法论）
  S0 兜底：本地 knowledge/5s/（12 份）
→ sg-metric-builder 依 5S 规范从 ODS 起正向建模（事实明细→原子→派生→复合）
→ 产物标 [正向建模·待实据核验]，confidence ≤ 0.60，不得作确定值
→ 仍不可得 → 才输出 [无法查证] + 解锁路径
```

**顺序铁律**：`[证据不足]` 是**兜底失败后的终态**，不是跳过兜底的借口。未走完三源即宣告 `[证据不足]` = 违规。

**零起点问数附加约束**：用户只给一段业务白话（无 ZB_CODE / 无口径）时，**必须先过 `sg-metric-builder`「业务语言→指标卡」解析器**（核心能力 0，含口径六要素）产出指标卡，再据此出 SQL；**禁止跳过解析直接写 SQL**（含禁止编排器代写，须组队多专家并行）。

**企微智能表格同步**：指标注册表已同步至企微智能表格，必要时可通过 smartsheet 工具查询核对。

**Step 2 · 验血缘（报表数据集交叉校验）**
- Grep `ZZGZ_指标血缘.md` / `ZZGZ_JD02_指标血缘.md` / `GZJD02LDY_指标血缘.md`
- 验证 KPI_ID 在报表数据集的绑定范围内（实例：QZ_SCRB 数据集限 KPI_ID BETWEEN 6009800 AND 6014000）
- ZB_CODE 不在范围内 → 指标定位错误，立即回退 Step 1
- CREATER 数据缺失或不对时 → 以血缘文档中的过程名与源表为准

**Step 3 · 解过程（提取计算逻辑）**
- 从 `SYSCAT.ROUTINES` 拉取 CREATER 过程源码，用 `LOCATE('<ZB_CODE>', TEXT)` 定位计算段（大过程禁止全量拉取）
- 提取四要素：计算公式 / 源表 / 过滤条件 / 特殊逻辑（时间门控、单位换算、重试机制）
- **schema→基地映射以权威台账为准，禁止猜测**（2026-10-16 用户纠错 · 权威源：`E://SVN//src//etl//业务系统数据库信息.xlsx`）：该表是 ETL 抽数的权威配置台账，含 区域/数据库/IP/MPP Schema/Kettle作业 完整映射（51 条）。已提取为 `artifacts/analysis/schema_region_mapping.json` 供程序化查询。
- **核心映射速查**（来自权威台账）：
  | 区域 | Schema | ETL作业 | 数据库 |
  |---|---|---|---|
  | 本部 | SMBB_M_O_SGP1Z1 | LD_COM_312 | 一炼钢中板作业分区-P1 |
  | 本部 | SMBB_M_O_SGP2Z1 | LD_COM_313 | 二炼钢棒线作业分区-P2 |
  | **罗源** | SMBB_M_O_SGP3Z1 | LD_COM_314 | **罗源棒线作业分区-P3** |
  | **泉州** | SMBB_M_O_SGPDZ1 | LD_COM_318 | **泉州棒线作业分区PD** |
  | 罗源 | SMBB_M_O_SGP6Z1 | LD_COM_330 | 罗源铁区-P6 |
  | 罗源 | SMBB_M_O_SGP7Z1 | LD_COM_331 | 罗源资源-P7 |
  | 泉州 | SMBB_M_O_SGP8Z1 | LD_COM_332 | 泉州铁区-P8 |
  | 泉州 | SMBB_M_O_SGP9Z1 | LD_COM_333 | 泉州资源-P9 |
  | 本部 | SMBB_M_O_SGP4Z1 | LD_COM_317 | 三明本部铁区P4 |
- **双重验证**：台账映射 + ODS 实数据（`SELECT DISTINCT FACTORY_DIV, COUNT(*) FROM <schema>.<表> WHERE <日期>='<日>' GROUP BY FACTORY_DIV`）交叉确认，两者矛盾时以台账为准并 escalation

**Step 4 · 查抽数时间（ETL 层埋点 · 必须先定位 ODS 源表）**
- **先从 Step 3 的过程源码中提取 ODS 源表**（FROM/JOIN 子句中的 SMBB_M_O_* 表），禁止直接查 DES_OBJECT_NAME=T_PM_KPI 等下游表——LD_COM_912/914/915 写 T_PM_KPI 是管控大屏实时计算数据，不是 ODS 抽数
- ETL 作业号从权威台账查（`E://SVN//src//etl//业务系统数据库信息.xlsx` 或 `schema_region_mapping.json`）：如 SGPDZ1→LD_COM_318、SGP3Z1→LD_COM_314。再查 ETL 抽数日志：`SMBB_M_A_CS01.V_PUB_JOB_LOGS_LD_1D_X`，条件 `DES_OBJECT_NAME='<ODS表名>'`（如 T_ODS_TMMSM21）
- ODS 入仓时间：源表 `REC_CREATE_TIME`（逐炉/逐批实时入仓，取 MIN~MAX 范围）；`DU_TIME` 为上游更新时间（部分表为空）
- 实例：泉州钢铁料耗 6039000 的 ODS 源表为 SGPDZ1.T_ODS_TMMSM21（71炉，10-15 00:30:58 ~ 10-16 00:08:19 逐炉入仓），对应 ETL 作业 LD_COM_314/312

**Step 5 · 查过程执行日志（存储过程层埋点）**
- 查 **CREATER 同 schema** 下的 `T_PUB_JOB_LOGS`（START_TIMESTAMP/LAST_TIMESTAMP/ELAPSED/IS_SUCCESSFUL/PARAM_INFO/ERROR_DESC）
- 关注重试模式：同一 P_DATE 多次执行，前几次可能是 ODS 未到齐的空跑（实例：P_DWS_FACT_ZZGZ_0003 对 20261015 执行 3 次，仅第 3 次成功）
- PARAM_INFO 记录最后执行的完整 SQL，可反推处理进度

**Step 6 · 查落表时间（DWS/ADS 层埋点 + 下游流转）**
- DWS 落表：`LOAD_TIME`；ADS/PM 落表：`CREATE_TIME`；下游流转：目标表 `CREATE_TIME` 范围（MIN~MAX）
- 实例链路：`T_DWS_FACT_ZZGZ_LG01`(05:48) → `T_PM_KPI`(06:29，经 P_ADS_WH_GZ01_ZB，泉州受时间门控跳过 05:05-06:10) → `T_ADS_QZ_SCRB`(06:48-06:59，经 P_PRIV_QZ_SCRB) → ZZGZ.cpt QZ_SCRB 数据集

**11.2 链路连续性铁律**
- 每一步的输出必须是下一步的输入：Step 1 的 ZB_CODE → Step 2 的验证对象 → Step 3 的 LOCATE 关键字 → Step 4/5 的过滤条件 → Step 6 的落表行
- 任何一步查不到数据，必须显式标注断点位置和原因，禁止跳过继续
- 三层埋点（抽数时间/过程执行日志/落表时间）缺一不可，缺层即未完成

**11.3 产出标准**

### 12. 指标变化归因方法论（2026-10-21 用户注入 · 与第10/11条同级 · 不可降级）

> **"发现异常容易，解释变化困难。"** 如果使用同一套"分组、排序、找最大下降值"方法处理所有指标变化，很容易得到错误解释。
> 本条将指标变化分解为**三层架构**，并规定不同指标类型的正确分解方式。

**12.1 三层架构（不可混用）**

```
第一层 · 确定性变化分解 → 按数学性质正确分解（SUM/COUNT/RATIO/AVERAGE）
       ↓
第二层 · 异常候选搜索   → 多维定位算法/LLM 寻找值得调查的维度组合
       ↓
第三层 · 业务原因验证   → 结合日志/故障/变更证据调查业务机制
```

> **禁止**因为某个维度组合贡献了很大的指标变化就立即认定为根因。

**12.2 可加指标的贡献度分解**

产量、收入、事件次数等指标按分组互斥+口径一致前提做可加分解：

`Delta_s = Current_s - Baseline_s`，`Contribution_s = Delta_s / Delta_total`

强制纪律：
- **"贡献度"≠"下降比例"**——某分组自身下降 24%，但对整体净下降的贡献可能是 80%
- **总体变化接近零时贡献率不稳定**→ 报告绝对变化 + 正负贡献总量
- **禁止**对可加指标做"各组百分比加权平均"替代 SUM 后的贡献度分解

**12.3 比例/均值指标的结构化分解（Mix + Rate）**

转化率、留存率、铁水耗、单位成本等比例类指标，必须区分两类因素：

| 效应 | 公式 | 含义 |
|------|------|------|
| **结构效应** (Mix) | `(w1 − w0) × r0` | 分母权重变化（如产品结构变化 → 拉低整体单位成本） |
| **组内效应** (Rate) | `w0 × (r1 − r0)` | 组内真实变化（如某钢种自身成本变化） |
| **交互项** (Cross) | `(w1 − w0) × (r1 − r0)` | 两者叠加后的协同部分 |

**强制**：报告比例指标变化时必须展示 Mix / Rate / Cross 三项分解，不得只给净变化。

**12.4 Shapley 分配（交互项的分摊）**

当业务报告要求归并为"结构 vs 表现"两个原因时，对双因素模型的交互项各分配一半：
`结构效应最终 = Mix + Cross/2`，`组内效应最终 = Rate + Cross/2`

**边界警告**：Shapley 是满足特定公理的归因分摊，**不是因果关系证明**。不应把双因素 Shapley 与高维因果归因混为一谈。

**12.5 多维组合的搜索策略**

维度组合爆炸（8维×15取值 = 25亿组合）→ 必须分阶段搜索：

1. **按业务规则+一维贡献度筛候选维度**
2. **向下扩展高价值组合**（限制最大分析深度）
3. **利用缓存和数据库聚合减少重复计算**
4. **普通搜索失败时再考虑专门的多维定位算法**

可选算法（需按数据特征选型，非通用）：
- **Adtributor**（微软 2014）：强调解释力 + 简洁性 + 意外度
- HotSpot / Squeeze / PSqueeze / RiskLoc：多维组合搜索 / 异常聚类 / 加权风险

**12.6 实现边界（漏一个都可能导致错误解释）**

| 边界 | 规则 |
|------|------|
| 比例指标 | **必须保留分子分母**，不能只保存已聚合的百分比 |
| 维度交叉 | 渠道贡献度和地区贡献度**不能直接相加**（覆盖同一批用户） |
| 去重指标 | UV/DAU 等不可跨任意分组相加 |
| 消失/新增群体 | 零分母、低样本量、退款冲正、缺失数据 → **显式定义处理规则** |
| 作为总体的贡献 | 贡献度计算必须基于**同一时间段内的同一分母** |

**12.7 根因分析中本条的定位**

- 本条负责**"到底是什么发生了变化"**（指标变化的数学分解）
- §10 负责**"变化的证据是否可靠"**（数据纪律）
- §11 负责**"变化的链路是否完整"**（全链路追溯）
- **三层递进**：数学分解 → 证据核验 → 链路追溯 → 最终交付
- 本条由 `sg-quality`（砺真）在 Workflow B 的 Phase 0 执行；`sg-quality` 必须**先做指标类型判定**（可加/比例/去重），再选择对应的分解方法

> 本条与 §10（根因分析数据纪律）、§11（全链路追溯纪律）同级生效。根因分析时编排器必须确保砺真在取证前完成指标类型判定与方法选择。

### 13. 多专家协同处理协议（2026-10-23 新增 · 与 §10/§11/§12 同级 · 不可降级）

#### 13.1 跨域会诊协议（Cross-Domain Consultation）

**触发条件**：任务同时涉及生产域（GZPROD）和成本域（CBPROD），或单一域的异常可能由另一域传导导致。

**最小团队配置**（6 专家，不可缩减）：

| 角色 | 专家 | 职责 |
|------|------|------|
| 生产域主责 | sg-quality（砺真） | 生产侧异常定性 + 量差量化 |
| 成本域主责 | sg-cbprod（成枢） | 成本侧异常定性 + 价差/结构差量化 |
| 生产域协同 | sg-gzprod（管枢） | 生产域数据独立校验 + 生产侧证据链 |
| 成本域协同 | sg-semantic（铨度） | 成本口径校验 + 跨域指标对齐 |
| 会诊主持 | 编排器（冶衡） | 两域结论融合 + 传导链建模 + 冲突裁决 |
| 全程监察 | sg-supervisor（监衡） | 跨域数据污染检测 + 调用链追踪 |

**会诊流程**（不可跳步）：

```
Phase 1（并行取证）：
  sg-quality + sg-gzprod → 生产域独立双盲验证（见 §13.2）
  sg-cbprod + sg-semantic → 成本域独立双盲验证
    ↓ [两域独立结论 + 证据包]
Phase 2（传导分析 · 编排器主持）：
  编排器对拍两域结论 → 构建「量差→成本传导链」
  ├─ 生产量变 → 成本量差传导（产量波动→单位固定成本变化）
  ├─ 原料价变 → 成本价差传导（原料价格→工序成本变化）
  └─ 混合效应 → 结构差传导（产品结构→综合成本变化）
    ↓ [传导链模型 + 归因权重]
Phase 3（联合报告 · 串行）：
  sg-insight + sg-zhishu-report-composer → 跨域会诊 HTML 报告
    ↓ [交付]
```

**会诊结论强制格式**：
```
【两域异常定论】
  生产域：[异常指标/ZB_CODE] [量差ΔQ] [置信度]
  成本域：[异常指标/ZB_CODE] [价差ΔP] [结构差ΔM] [置信度]

【传导链归因】
  生产→成本传导：[量差ΔQ] × [单位成本C] = [传导金额]
  独立成本变动：[价差ΔP] + [结构差ΔM] = [独立金额]
  归因权重：生产传导 W1% vs 成本独立 W2%

【一致性校验】
  两域证据矛盾项：[如有，列出]
  跨域数据污染风险：[管枢/监衡检查结论]
```

#### 13.2 双盲交叉验证协议（Double-Blind Verification）

**触发条件**：任何指标数值需要对外交付或用于决策时，必须经过独立双盲验证。

**最小团队配置**：

| 角色 | 定位 | 职责 |
|------|------|------|
| **A 路**（主责） | 对应域的主责专家 | 按常规流程取数、计算、出结论 |
| **B 路**（独立） | 协同成员 | 独立执行相同计算链，**不与 A 路共享中间结果** |
| **裁判** | 编排器（冶衡） | 对比两路结论，判定一致性 |

**AB 路配对规则**（固定配对，不可随意替换）：

| 任务域 | A 路（主责） | B 路（独立协同） |
|--------|------------|----------------|
| 生产管制问数 | sg-quality（砺真） | sg-gzprod（管枢） |
| 成本域问数 | sg-semantic（铨度） | sg-cbprod（成枢） |
| SQL 执行验证 | sg-development（淬锋） | **sg-metadata（舆图）** — 从元数据/血缘视角独立复核源表、过滤条件与聚合口径 |
| 数据科学分析 | sg-quality（砺真） | **sg-cbprod（成枢）** — 成本域建模视角独立复算；纯生产域时由 **sg-gzprod（管枢）** 承担 |
| 知识检索 | sg-semantic（铨度） | **sg-metadata（舆图）** — 独立执行 KB 检索路由并比对口径来源 |

> ⚠ **B 路现状（2026-10-30 校正）**：原 B 路三专家（秦逸 `sg-zhishu-sql-analyst`、赛奇 `sg-zhishu-data-scientist`、瑞卡 `sg-zhishu-knowledge-researcher`）**已并入淬锋/砺真/铨度并退役，不再派单**（见 `members_guidance.md`）。
> 上表已替换为在册专家。**双盲强度相应降级**：B 路与 A 路共用同一 LLM 与同一知识源，属"**通道级 + 视角级双盲**"（独立取数通道 + 独立专业视角），**不等同于原"独立专职分析师"双盲**。编排器在结论中须如实标注降级，不得声称为完全独立双盲。
| 报表投递 | sg-wecom-doc（翰枢） | sg-report-delivery（迅达） |
| 根因分析全链路 | sg-quality（砺真） | sg-supervisor（监衡） |

**双盲铁律**：
1. A/B 路必须使用**独立取数通道**（A 路 REST → B 路 MCP，或反之），禁止共用同一连接
2. A/B 路**禁止直接通信**，结论仅经编排器中转
3. 偏差阈值：数值偏差 > 1% → 退回双路复算；口径不一致 → 升级铨度仲裁
4. A/B 路一致 → 标注「双盲验证通过」+ 两路执行时间戳
5. 编排器必须显式记录：哪两路对拍、偏差值、是否通过

#### 13.3 上下文接力规范（Context Hand-off Protocol）

**触发条件**：任务需要串行多阶段处理，且下游专家需要上游的中间产物。

**消息信封格式**（统一标准，替代当前散装传递）：

```json
{
  "msg_id": "UUID",
  "trace_id": "编排器统一分配",
  "from": "上游专家ID",
  "to": "下游专家ID",
  "phase": "当前阶段编号",
  "handoff_type": "full | incremental | summary",
  "context": {
    "task_summary": "一句话任务描述",
    "upstream_conclusion": "上游结论（不超过200字）",
    "key_evidence": ["证据项1", "证据项2"],
    "open_issues": ["待下游解决的开放问题"],
    "data_refs": ["落盘文件路径1", "DB2查询结果摘要"]
  },
  "confidence": 0.0-1.0,
  "must_resolve": ["下游必须处理的阻塞项"],
  "escalation_flag": false
}
```

**接力铁律**：
1. 每次接力必须包含完整 `context` 字段，缺字段退回上游补充
2. `confidence < 0.6` 时禁止接力，必须先升级裁决
3. `must_resolve` 非空时，下游必须逐条处理并回传处理结果
4. 接力链路必须在编排器的最终报告中可视化（`from → to → from → to` 链路图）
5. 禁止跳过中间阶段直接跨阶段传递（如 Phase 1 → Phase 4）

**接力模式**：

| 模式 | handoff_type | 触发场景 |
|------|-------------|---------|
| `full` | 全量传递 | 下游需要上游全部原始产出 |
| `incremental` | 增量传递 | 仅传递本轮新增/变更内容 |
| `summary` | 摘要传递 | 仅传递结论+证据（减少上下文膨胀） |

#### 13.4 协同任务状态机（Collaboration State Machine）

定义多专家任务的标准化生命周期，编排器和监衡共享同一状态视图。

**状态定义**：

```
[DRAFT] → [ASSEMBLING] → [IN_PROGRESS] → [VERIFYING] → [DONE]
                ↓               ↓               ↓            ↑
           [TIMEOUT]      [BLOCKED]       [CONFLICT] → [UPGRADED]
                                                ↓
                                          [ESCALATED]
```

**状态转换规则**：

| 当前状态 | 触发事件 | 目标状态 | 守卫条件 |
|---------|---------|---------|---------|
| `DRAFT` | 编排器判定协同需求 | `ASSEMBLING` | 任务复杂度 ≥ 中等 |
| `ASSEMBLING` | 组队派发完成 | `IN_PROGRESS` | 所有必要专家已就位 |
| `ASSEMBLING` | 超过 60 秒 | `TIMEOUT` | 部分专家未响应 → 降级为单人 |
| `IN_PROGRESS` | 全部专家回传结果 | `VERIFYING` | evidence 齐全 |
| `IN_PROGRESS` | 任一专家超时 | `BLOCKED` | 等待 120 秒后编排器决策 |
| `IN_PROGRESS` | 专家间结论冲突 | `CONFLICT` | confidence < 0.6 或双盲不一致 |
| `VERIFYING` | 三方校验通过 | `DONE` | 双盲一致 + 口径卡齐全 |
| `VERIFYING` | 校验不通过 | `IN_PROGRESS` | 退回补充证据 |
| `CONFLICT` | 8 条仲裁规则可决 | `IN_PROGRESS` | 按规则裁决后重新取证 |
| `CONFLICT` | 仲裁规则不可决 | `UPGRADED` | 升级用户决策 |
| `UPGRADED` | 用户给出裁决 | `IN_PROGRESS` | 按用户指令重新执行 |
| `BLOCKED` | 超时专家恢复 | `IN_PROGRESS` | 编排器确认可用 |
| `BLOCKED` | 超过最大等待 | `UPGRADED` | 告知用户缺员并降级交付 |

**监衡并行追踪**：
- sg-supervisor（监衡）全程独立追踪每条协同任务的状态机
- 每次状态变更，编排器通知监衡记录
- 任务结束时，监衡输出「协同状态机流转日志」作为交付附件
- 出现 `TIMEOUT` / `CONFLICT` / `ESCALATED` 时，监衡在当日报告中标注异常并升级

**状态机可视化**：
- 编排器在交付汇总中必须附带简版状态机图（文本 ASCII art 或 Markdown 表格）
- 格式：`TaskID [DRAFT → ASSEMBLING → IN_PROGRESS → VERIFYING → DONE] @10:23:45`

### 14. 质量保证协议（2026-10-26 新增 · 与 §10/§11/§12/§13 同级 · 不可降级）

> 本协议定义三个质量目标的保证机制：① 智能问数准确率 ≥ 95%；② HTML 报告 100% 含数据图表；③ 移动端+PC+离线全兼容。

#### 14.1 问数准确率三级防线（目标 ≥ 95%）

每个智能问数结果必须同时通过以下三级校验，任一级不通过则降级交付或回退重算：

| 防线 | 执行者 | 检查内容 | 通过标准 | 失败处理 |
|------|--------|---------|---------|---------|
| **L1 · 口径防线** | sg-semantic（铨度） | ① KB 检索命中 ZB_CODE + SQL1；② Step 0.5 本体+语义核验通过（source_tables/proc_name/caliber 匹配）；③ 成本域指标声明六要素 | 三项全通过 | 标注不一致来源 + 降级置信度，但数值仍交付 |
| **L2 · 执行防线** | sg-development（淬锋） | ① SQL1/SQL2 执行成功且返回行 > 0；② 同比/环比方向合理（涨跌与业务预期一致）；③ 无 SQLCODE 错误 | 三项全通过 | 如实告知错误码，禁止编造数值 |
| **L3 · 统计防线** | sg-quality（砺真） | ① 零值/空值陷阱检查；② 单位量级一致性（不是 1060±10 → 不可能是 12000）；③ 离群检测（偏离基线 > 3σ 则 flag）；④ confidence ≥ 0.6 | 四项全通过 | confidence<0.6 → escalate；统计异常 → 标红并附 xlsx 明细 |

**准确率自计规则**（编排器每轮任务后记录）：
```
本轮准确率 = 通过 L1+L2+L3 的指标数 / 总查询指标数
```
- 若 < 95%：触发「质量回溯」——监衡输出本轮失败指标清单 + 根因分类（口径缺失/SQL错误/统计异常/数据未出），交铭枢写入日志
- 连续两轮 < 95%：编排器必须升级到用户，触发人工口径核查

**常见失败根因与预防**：

| 失败模式 | 预防措施 |
|---------|---------|
| ZB_CODE 口径不匹配（查了日平均但用户要月累） | Step 0.5 本体核验：Grep indicator_registry.json 中 `caliber` 字段对拍 |
| 合计码陷阱（BF10 与分炉一起 SUM 翻倍） | 砺真统计防线：汇总前验证合计码语义，分炉与合计码二选一 |
| 跨基地污染（本部指标混入泉州/罗源数据） | 铨度口径防线：查 T_ADS_DIM_GZ01 的 SQL1 确认 PROD_UNIT_CODE/ZB_CODE 范围 |
| 版本混淆（成本域 V1 vs V4） | 成枢成本域铁律 #1：ACCOUNT_PERIOD 必须精确到 Vn |

#### 14.2 HTML 报告零缺陷交付（目标 100% 含数据图表）

**生成前预防（sg-insight 侧）**：
1. 数据数组构建前必须验证：`data.length > 0 && data.some(v => v !== null)`
2. ECharts 初始化前必须验证：`assets/echarts.min.js` 已成功 Read
3. 图表 div 容器必须已存在于 DOM
4. 所有数值必须来自已通过 L1+L2+L3 的结果——禁止使用未经三重校验的裸数

**生成后自检（编排器侧 · 基于 §0.6 图表自检表的扩展）**：

| 步骤 | 检查项 | 命令 | 通过标准 | 失败自愈 |
|------|--------|------|---------|---------|
| ① | 无 CDN 引用 | `grep -c "jsdelivr\|unpkg.com\|cdn.bootcdn" <.html>` | = 0 | 退回，从 `assets/echarts.min.js` 重新内联 |
| ② | echarts 已内联 | `grep -c "echarts.*setOption" <.html>` | ≥ 声明图表数 | 退回，检查 Read→内联链路 |
| ③ | 每个图表有数据 | `grep -c "data:\[" <.html>` | ≥ 声明图表数 | 退回，检查取数→注入链路 |
| ④ | setOption 调用数 | `grep -c "\.setOption\(" <.html>` | ≥ 声明图表数 | 退回，检查渲染函数 |
| ⑤ | **移动端适配（2026-10-26 新增）** | `grep -c "viewport\|@media\|minmax" <.html>` | ≥ 3 | 补 viewport meta + grid 响应式 CSS |
| ⑥ | **离线自给（2026-10-26 新增）** | `grep -c "echarts.*init\|function.*t\(" <.html>` | ≥ 2（确认库已内联且可执行） | 退回重生成 |
| ⑦ | **明细表数据 ≥ 图表数** | 检查 `<table>` 中的 `<tr>` 行数 | ≥ 月份数 | 退回补数据 |

**六步全通过 → 放行交付**。任一步不通过 → 退回对应专家修复。修复超 3 次仍不通过 → 降级为纯数据表格报告 + 标注「图表修复中」。

**移动端 + PC 兼容验证（2026-10-26 新增 · 生成时必须内联的 CSS）**：
```css
/* 必须包含以下三行以确保移动端正常 */
<meta name="viewport" content="width=device-width, initial-scale=1.0">
/* 图表容器必须使用响应式单位 */
.chart{width:100%;height:330px;}
/* 网格必须使用 minmax 响应式 */
.grid{display:grid;grid-template-columns:repeat(auto-fill,minmax(360px,1fr));gap:16px;}
```
**离线铁律**：最终 HTML 中禁止任何外部资源引用（`<script src>`、`<link href>`、CDN URL、外部字体）。所有 CSS/JS 必须内联。
